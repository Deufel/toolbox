color engine

Color is a position, not a palette

There are no named colors in this system. An element declares where it sits on two signed axes — --bg for its surface, --fg for its ink — and the engine resolves the actual OKLCH lightness, chroma and contrast against whatever surface it lands on, in whatever theme and hue are live. Drag the header hue and flip the theme: everything below re-resolves.

--bg · surface−1 … 0 … +1
0 is the base surface. Negative recedes it (toward the floor — quieter, darker in light / deeper in dark). Positive advances it toward the chromatic peak (louder, saturated in the live hue). It's a depth position, not a swatch.
--fg · ink−1 … 0 … +1
Negative pushes ink to the neutral contrast pole (max legibility, either theme). Positive pushes it to the chromatic pole (colored ink in the hue). The engine always solves contrast against the host surface's lightness, so ink stays readable as the surface moves.

Shift a subtree's hue — semantics don't budge

--hue-shift adds into --_h, so it rotates every non-locked descendant at once — a whole panel can re-hue with one declaration. Semantic elements pin --hue-lock, which wins the fallback, so .suc/.inf/.wrn/.dgr are immune. Drag it: the generic surfaces sweep, the meaning-carrying chips hold.

Relative lift keeps controls legible anywhere

A default <button> doesn't pin a surface — it sets --lift, sitting a step above whatever hosts it. So the same button reads correctly on every surface below, no variants.

Semantic locks

.suc / .inf / .wrn / .dgr lock the hue and commit ink to the chroma pole (via --_sem-ink) — layer-independently, so a tag, an alert and a button all speak the same meaning.
