Authoring your own components

The system covers most needs with primitives and components. When you need something it doesn't ship — here, a calendar — this is the method. We build one, step by step.

The method

Before writing anything, know the order of preference. It keeps custom work small and predictable:

  1. Compose primitives first. .row, .column, .grid and the rest cover most layouts.
  2. Reach for a scoped block when a section needs a shape no primitive gives — a one-off grid template. Co-locate the CSS with the markup using @scope.
  3. Lift to a component only when the same scoped block appears three times. Until then, scoped is the right home.

A calendar is a good test: it needs a real grid (a primitive won't do), it needs token-driven color for today and muted days, and it is the kind of thing you would eventually lift into a component. We will walk all three stages.

Step 1 — sketch the shape

A month is a seven-column grid: one column per weekday, a row of weekday labels on top, then the day numbers. That is the whole structure. A layout primitive can't express "seven equal columns," so this is a legitimate case for a scoped grid.

Start with the scope and the wrapper. The system's rule is to never style :scope directly — put the grid on a child so viewport and page-slot classes on the outer element don't collide with it.

<section>
  <style>
    @scope {
      :scope .cal-grid {
        display: grid;
        grid-template-columns: repeat(7, 1fr);
        gap: 0.15lh;
      }
    }
  </style>
  <div class="cal">
    <div class="cal-grid">…</div>
  </div>
</section>

The gap is 0.15lh — derived from line-height, like every gap in the system. No pixel value, no spacing token.

Step 2 — the weekday header and the days

Fill the grid. Seven weekday labels, then the day numbers as cells. Each cell type is targeted by structure inside the scope — .cal-wd for the labels, .cal-day for the days — no invented styling hooks beyond the two the markup genuinely needs.

:scope .cal-grid > .cal-wd {
  --type: -2;            /* smaller than the day numbers */
  --fg: -0.5;            /* quiet — these are labels      */
  text-align: center;
  padding-block: 0.3lh;
}
:scope .cal-grid > .cal-day {
  display: grid;
  place-items: center;
  aspect-ratio: 1;       /* square cells                  */
  --type: -1;
  border-radius: var(--cfg-radius);
}

The day cell is aspect-ratio: 1 — square regardless of column width — with the number centered by a one-line grid. Sizing is --type, the corner is the system's radius token.

Step 3 — color with tokens

A calendar has two special days: ones outside the current month, and today. Neither needs a literal color. Muted days lower the ink with --fg; today paints a surface with --bg. Both adapt to theme and brand hue for free.

/* days spilling in from the neighbouring month */
:scope .cal-grid > .cal-day.cal-muted { --fg: -0.3; }

/* today — a painted surface, loud */
:scope .cal-grid > .cal-day.cal-today {
  --bg: 0.8;
  --fg: -1;
  font-weight: 700;
}

/* hover — a soft surface lift */
:scope .cal-grid > .cal-day:hover { --bg: 0.15; }

Nothing here names a color. "Today" is just a cell with a loud surface; "muted" is just dimmer ink. Switch the theme or change --hue and the calendar follows, because the cells were described in the system's terms, not in hex.

Step 4 — the header, from a primitive

The month label and the previous/next controls don't need scoped CSS at all — that is a left/right arrangement, and .lcr already does it. Reach for the primitive before writing anything.

<div class="cal-head lcr">
  <button class="icon-btn" aria-label="previous month">‹</button>
  <strong>March 2026</strong>
  <button class="icon-btn" aria-label="next month">›</button>
</div>

No scope entry was needed for the header. When a primitive fits, the primitive wins — that is step one of the method, applied.

When to lift it into a component

The calendar above lives in a scoped block on one page. That is the correct home for it — for now. The signal to promote it to a real component is repetition: the same scoped block copied into a second page, then a third.

At that point, move the rules out of @scope and into the framework's component layer under a class — the markup stops carrying a <style> block and just uses .cal. Nothing about the CSS changes; only its home does. Lifting early — before the third use — adds a component nobody else needs yet.

/* once it has earned its place: */
@layer component.complex {
  .calendar { … }   /* the same rules, now framework-wide */
}

Compose first, scope when a primitive won't reach, lift when it repeats. That order is the whole method — the calendar was just a place to watch it work.
