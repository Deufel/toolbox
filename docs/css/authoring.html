Authoring your own components

The system covers most needs with primitives and components. When you need something it doesn't ship — here, a calendar — this is the method. We build one, step by step.

The method

The layout primitives are meant to cover what you need. .row, .column, .grid, .ngrid, .lcr, .hero and the rest are the toolkit — most interfaces are built entirely by composing them, and that is the intended path.

Sometimes a real, specific requirement resists every primitive — a one-off layout a particular customer needs. When that happens, the recommendation is to reach for @scope rather than scatter a handful of throwaway utility classes across the codebase.

This is a guard against CSS technical debt. A scoped block stays co-located with its markup and never leaks vocabulary into the global namespace — the one-off stays a one-off. A pile of single-use utility classes does the opposite: it spreads, and the next person reuses a class that was never meant to be reused. Quarantining the exception is how the system matures responsibly.

We will build a calendar. It turns out to need no @scope for layout at all — and seeing why is the lesson.

Step 1 — recognise the shape

A month is a seven-column grid: one column per weekday, a row of weekday labels, then the day numbers. So the question is which primitive gives an explicit seven-column grid.

.grid is the responsive one — it auto-fits as many columns as fit above --grid-min, and you don't say how many. That is the wrong tool here; a calendar is always seven columns. The right tool is .ngrid, the explicit-size companion: you state the count with --cols.

<div class="ngrid" style="--cols: 7">
  <!-- 7 columns, exactly -->
</div>

If the framework had lacked an explicit-grid primitive, that absence would be the real finding — the honest fix would be to add .ngrid to the system, not to write a scoped grid on this one page. A missing primitive is a framework gap; closing it with a primitive keeps every future calendar a one-liner.

Step 2 — the cells

The grid is composition. What is left is genuinely calendar-specific: a square day cell with a centred number, and a quieter weekday label above it. That is not a layout gap — no primitive should know what a "day cell" is — and it is small. This is the legitimate, contained use of @scope.

Target by structure, and do not manufacture configuration variables. A day cell is just a cell; styling it does not need a --day-size or a --cell-radius knob, because nothing downstream varies. Write the values where they are used.

@scope {
  /* weekday labels — quiet, small */
  :scope .cal-grid > .cal-wd {
    --type: -2;
    --fg: -0.5;
    text-align: center;
    padding-block: 0.3lh;
  }
  /* day cells — square, centred number */
  :scope .cal-grid > .cal-day {
    display: grid;
    place-items: center;
    aspect-ratio: 1;
    --type: -1;
    border-radius: var(--cfg-radius);
  }
}

Targeted by structure — .cal-wd, .cal-day — with no invented hooks beyond the two the markup genuinely needs. Sizing is --type, the corner is the system's radius token. No pixels, no dummy variables.

Step 3 — color with tokens

A calendar has two special days: ones spilling in from a neighbouring month, and today. Neither needs a literal color or a variable. A muted day is just lower ink; today is just a painted surface. They are plain classes that nudge --fg and --bg.

/* days from the neighbouring month — quiet ink */
:scope .cal-grid > .cal-day.cal-muted { --fg: -0.3; }

/* today — a loud painted surface */
:scope .cal-grid > .cal-day.cal-today {
  --bg: 0.8;
  --fg: -1;
  font-weight: 700;
}

/* hover — a soft surface lift */
:scope .cal-grid > .cal-day:hover { --bg: 0.15; }

Nothing here names a color. "Today" is a cell with a loud surface; "muted" is dimmer ink. Switch the theme or change --hue and the calendar follows, because the cells were described in the system's terms.

Step 4 — the header

The month label with previous/next controls is a left/centre/right arrangement, and .lcr already does that. No scoped CSS, no thought — the primitive fits, so the primitive is the answer.

<div class="lcr">
  <button class="icon-btn" aria-label="previous month">‹</button>
  <strong>March 2026</strong>
  <button class="icon-btn" aria-label="next month">›</button>
</div>

Grid from .ngrid, header from .lcr, every colour and size from a token. The only bespoke CSS is the small scoped block for cell appearance — and even that invents nothing. Here it is, running:

When @scope is the right call

The calendar needed @scope only for cell appearance — small, contained, no layout gap. But some requirements are larger one-offs: a print résumé, a specific report layout, a fixed-format document a single client asked for. A layout that exists exactly once, that no primitive was built for.

That is what @scope is for, and the discipline is the same as the calendar's, scaled up:

  • Co-locate it. The <style> block sits inside the element it styles. The CSS travels with the markup; it is obvious it belongs to that one section.
  • Target by structure. Style article h3, article ul, article > div span — real elements by their place in the tree. Do not invent class names to hang styles on.
  • Do not manufacture variables. A one-off has nothing downstream to vary and nothing to override. A value used once, in one place, is just a value — write it inline. Lean on the units and tokens that are already inherited; do not build a configuration surface for something with a single instance.
  • Never style :scope directly. Put layout on a child — :scope > div — so viewport classes and page-slot classes on the outer element do not collide with it.

The point is not that scoped CSS is elegant. It is that the one-off stays contained: co-located, namespaced to its subtree, impossible to reuse by accident. That is why it beats a scatter of utility classes — the debt is quarantined, not spread.

If you find yourself reaching for @scope often, that is the signal — not that you are using it wrong, but that the framework has a gap. A recurring need is a missing primitive. Close it the way .ngrid closed the explicit-grid gap, and the next person never has to scope it at all.
